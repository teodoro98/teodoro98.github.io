Nine disruptions in ten days: what happened at GitHub

From 26 October to 4 November errors and delays on Git, the API, Actions and webhooks, with the causes GitHub has published and the documentation's advice.

Teodoro Corbo5 November 2026, updated 8 November

On the morning of 4 November we get an urgent call because the pipelines won’t start. Git answers “Permission denied”, and the first suspects are us, our keys and our permissions. After the checks, only one suspect is left. GitHub’s status page shows an incident on Git, the API, issues, pull requests and Actions, opened around 11:00 and closed around 13:00. For those two hours our pipelines stay stuck.

That disruption is one of the nine. In Stack Overflow’s 2025 survey, 8 in 10 of the developers who answered say they use GitHub, and over the past year, the company says, Actions ran an average of 124 million jobs a day. This disruption, like three others, has no published cause yet.

The same “Permission denied” for other developers

A minute after the incident opened, “Tell HN: GitHub Is Down” went up on Hacker News. Another thread passed a hundred comments. Users described clones and fetches that worked on and off, and over SSH Git answered like this.

$ git pull
git@github.com: Permission denied (publickey).
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.

The message asks you to check your access rights and that the repository exists. Some thought their SSH key had been breached, or that they had been hacked. One user wrote that their CircleCI deploys were stuck too, because they couldn’t fetch the code.

On the platform’s forum, GitHub Community, a discussion started a few minutes after the incident began got about twenty replies in two hours. It happened with RSA, Ed25519 and ECDSA keys, and the same key would sometimes work and sometimes get “Permission denied”. Around noon one user posted “I couldn’t push for 2 hours, but now it worked!”

In the afternoon a change paused event delivery

Around 17:00 the status page reported a second incident, on Actions, Pages and webhooks: events that trigger Actions had a problem, and job status updates could arrive late. Shortly after 18:00, in the official incident thread on the forum, GitHub declared it resolved. Less than forty minutes later another incident on Actions appeared, with the same description. In the same thread, after the announcement, three users reported that the problem was still there.

On 7 November the company published a single explanation for both incidents. A configuration change to an internal event-routing service had paused delivery of several event streams. The change depended on feature flags that were not set up as intended, which the service did not handle gracefully. The configuration change was rolled back, but the code change itself stayed, and a later deployment brought it back. It took a second rollback.

Twice, for about an hour and a half in all, Actions workflow runs and job status updates were delayed by up to 25 minutes, and Pages deployments dropped to about 4% of normal. Webhooks, Code Scanning and the Copilot coding agent were delayed too; the delayed events were processed afterwards. The company has announced that a misconfigured flag can no longer pause delivery, and that a check before each deployment will verify that every flag exists.

On 3 November excess connections slowed Git over HTTPS for more than seven hours

Clones, fetches and pushes over HTTPS were slow, and some failed. For about half of that traffic, median response time rose from under 100 milliseconds to as high as 5 seconds. Git over SSH was not affected. On the status page the incident appeared at 21:57, almost six hours after it began.

Excess connections had built up on the hosts that serve that traffic and saturated their network capacity. At its load balancers GitHub blocked a client traffic pattern, then reloaded them, which released the connections. The block also kept some users of one third-party integration from using Git over HTTPS, until it was removed at 14:26 on 4 November. Planned next: earlier alerts when Git over HTTPS stays slow, and load balancer mitigations that also apply right away to connections already open.

Every service hit at least twice

The nine disruptions fall on five days. Actions is hit five times, the other services at least twice. The platform rates more than half of them as major or critical. The first of the nine, on 26 October, appeared on the status page only after it had ended.

On 30 October Android Authority wrote, judging by reports on Downdetector, that it was the second time that day GitHub had gone down. On Hacker News the thread on the second disruption drew 62 comments, including “My Actions are stuck waiting”.

On 27 October a migration and a cleanup overlapped

GitHub Apps are the applications that work on the platform with their own token. For about an hour, on average a little over one in a hundred of their Git operations got a 404, the “not found” code, for repositories that existed. In GitHub’s guide, a repository “not found” means it doesn’t exist or you don’t have permission to see it.

Shortly before 6:00 a cleanup job started deleting installation records of GitHub Apps. Meanwhile seven tables were being moved between two MySQL clusters, one in Virginia and one in the Central US region of Azure. Azure is the cloud of Microsoft, which has owned GitHub since 2018. The cleanup delayed the copying of data between the two clusters, by up to an hour at peak. When reads switched to the new cluster, around 8:00, the wrong 404s began.

GitHub, incident report of 27 October

On the status page the disruption appeared in the evening, more than twelve hours later, with impact “none”. Two fixes were announced: no more cleanup jobs during migrations, and a switch to a new cluster will stop when the copy is lagging.

On 30 October repeated retries saturated a gateway

In the evening Actions, Pages and webhooks were delayed for about forty minutes. Maintenance was under way on a network gateway that connects an Actions service to Redis clusters in Azure Central US. The service’s Redis client “retried aggressively”, in what GitHub calls a connection storm. The gateway saturated and about 90% of connection attempts were failing. Other services sharing the same network path were degraded as well.

It wasn’t the first time. Since August, retries appear in four incident reports, among the causes of a disruption or among what made it worse.

  • 17 August7 hours and 47 minutes of errors on the web and the API. Load balancers in GitHub's Central US datacenter saturate, and retries make it worse. InfoWorld and BleepingComputer covered it.
  • 13 Septembera retry loop around token creation keeps resending writes that are failing.
  • 19 Octoberan Actions service loses its cache connections and retries them from every server at once.
  • 30 Octoberthe Redis client saturates the gateway.

Each time, the fixes include a change to how retries work. After 30 October the company says it has already reduced connection retries. It is “further improving retry behavior with jittered backoff, shorter connect timeouts, and retry budgets”.

A year at 25 incidents a month

Over the last year 294 incidents were published, Copilot and Dependabot included. The jump came in winter, and since April the count has stayed around 25 a month, except in September. In the ten days from 26 October, counted the same way, there are 14: 1.4 a day against 0.8 over the year.

In April the CTO, Vlad Fedorov, wrote on the blog that from the second half of December 2025 work done with AI agents grew sharply, and that the company now designs for thirty times its current scale, with availability first. Growth like this, he explained, “does not stress one system at a time”: at high scale small inefficiencies compound, and “retries amplify traffic”.

In May LeadDev asked “What’s gone wrong at GitHub?” and reported that Zig had moved to Codeberg and that Mitchell Hashimoto had announced his Ghostty project would leave.

On 28 October, at its Universe conference, the company said it had added 4 million cores and 160 petabytes of storage this year, and expects to complete the move to multiple Azure regions early next year. The Octoverse report, out the same day, found that as of September more than 40% of pull requests started from an agent. According to The Register, the growth had caught the platform unprepared and led to a series of outages.

The causes GitHub has promised

Four disruptions still have no cause, including the one during our two hours. Closing them, the company promised on the status page a detailed root cause analysis as soon as it is available; for three others it published one on 7 November. For the burst of errors on the afternoon of 30 October, while investigating, it had pointed to “a temporarily overloaded component”.

What the documentation recommends

For automations that depend on the platform, the GitHub and Git documentation say what to do.

  1. Retry with pauses and a limitWhen requests are rate-limited, respect retry-after and x-ratelimit-reset. If they are missing, wait at least a minute and then longer and longer, with a maximum number of attempts, and make requests in series. Git retries on its own only after a 429, “too many requests”, and only if configured with http.maxRetries, which defaults to zero; for other errors its documentation has no retry options.
  2. Redeliver lost webhooksA failed webhook is not redelivered on its own: it has to be redelivered by hand or with a script that uses the redelivery API. Respond to webhooks within 10 seconds, and process the payload in a queue.
  3. Read a 404 with careIf you poll a resource and it keeps returning a 404, don't request it on every poll. First make sure the 404 is not caused by authentication or authorization, then wait much longer before you check again, or check again only when you have reason to believe the resource now exists.
  4. Keep a copy of the code in houseGit lets you keep an internal mirror, with git clone --mirror kept up to date by git remote update, and have automations read from it with url.<base>.insteadOf.
  5. Update SSH clients before 9 DecemberThat day the platform will run a trial shutdown of the ssh-rsa signature with SHA‑1 and of the diffie-hellman-group-exchange-sha256 key exchange, which will be removed for good from 13 January 2027. A client with RSA and SHA‑2, such as OpenSSH 7.2p1 or later, is enough, with the same keys; if you can't update, you can use an Ed25519 or ECDSA key. https:// remotes are not affected.

How the disruptions are counted. They are the incidents published on the status page, starting between 26 October and 4 November, on Git, the API, Actions, webhooks, Pages, pull requests or issues; the five that affect only Copilot or Dependabot are left out. The year's count, from 5 November 2025 to 4 November 2026, includes them all. Times are Italian time.
